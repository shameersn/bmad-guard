# Create or Update an FRD

## What Success Looks Like

`{feature-folder}/{agent.frd_filename}` exists for the PRD feature the user chose. It follows the template (all 13 sections, in order), with every `<placeholder>` replaced and every *italic* guidance note removed, including the template's "How to use this template" section, its title line and its "Guarded BMAD rules" note. Every requirement in it belongs to this PRD feature and can be traced to a source or to the user. Every unknown is counted: a `Q-<n>` in Section 12 or an `[ASSUMPTION A-<n>: …]` tag. The cross-reference check below passes or its gaps are listed to the user. The FRD's front matter is complete and `approval_status` is `draft` (the team override may move it to `review` afterwards). The user knows the confidence score, the open question and assumption counts, and what happens next.

## Non-Negotiables

- Never write `approval_status: approved`, `approved_by`, `approved_at`, a `Resolved:` line or an `[ASSUMPTION-RESOLVED …]` tag. The guards block these writes; do not try another way.
- Never renumber, reuse or remove a `Q-<n>`, `A-<n>`, `FR-<Fnnn>-<nn>` or `FNFR-<Fnnn>-<nn>` id, also on an update. A requirement that is dropped stays, marked *Withdrawn*. A question that is no longer relevant stays, and the user resolves it (for example "Resolved: No longer needed, the PRD dropped bulk edit. — <name>, <date>").
- Never add scope that is not in this PRD feature. Something the sources or the user want that the feature does not cover becomes a question that names it.
- Never change a PRD NFR target. If this feature cannot meet it, add a question.
- Never edit the PRD, the UX design, the architecture, another FRD or the FRD review. If a source looks wrong, say so to the user and add a question.
- Figma links and ADO ids are optional. Use them when the sources or the user give them; otherwise write "Not linked". Never add a question or assumption only because a Figma link or ADO id is missing.
- No real personal, patient or customer data in examples, sample values or UI text. Use made-up values.

## Approach

### Logging convention for this flow

Log through `skill:agent-project-logger`. Every call passes `--stage "frd"`, `--agent "experion-frd/CF"`, `--user "{user_name}"` and `--doc-path "<FRD path>"`. Never put FRD content, questions or answers in a log call: one short action line only. The team override logs the start and the end of the workflow; this flow logs only what the override does not.

### 1. Find the feature, the template and the sources

- The PRD is the one the team override's Sentry check approved. Read it in full.
- Ask which feature if the user did not say. The feature id `F-<nnn>` is the one the PRD writes on the feature's heading. If the PRD's features carry no `F-<nnn>` ids, stop: tell the user the PRD needs feature ids first (the PRD team override asks for them) and that they can be added through `bmad-prd`'s update intent. Do not invent ids.
- `{feature-folder}` is `{agent.frds_dir}/F-<nnn>`.
- Template: if `{agent.project_template}` exists, use it and tell the user so in one line; otherwise use `{agent.frd_template}`.
- Load the UX design and the architecture from `{planning_artifacts}` if they exist. A missing UX design or architecture is not a stop: say so, and every screen or technical fact that would have come from it becomes a question.
- If `{feature-folder}/{agent.frd_filename}` exists, this is an **update**: read it fully first. Keep its ids, its version history and its open items.

### 2. Draft section by section

Work in the template's order. After each group of sections, tell the user in one line where you are (for example "Sections 1-3 drafted; starting Section 4, 6 requirements").

- **Header.** FRD ID `FRD-<project code>-<Fnnn>` (ask the user for the project code once if no source gives it). Source PRD with its version and approval date. PRD Feature id and name. ADO ids as given, else "Not linked". Generated by "FRD agent (Fenn, `experion-frd`)". Version history: add one row per update.
- **Section 1-3.** From the PRD feature, its user journeys and the PRD's vision and users. Section 3 is a Mermaid flowchart: one subgraph per role or system, the entry points from 2.1, each decision, the hand-offs from 2.2.
- **Section 4.** One `4.<n>` block per capability of this feature, headed `FR-<Fnnn>-<nn> — <verb phrase>`. A new requirement takes the next free number, even when it is inserted mid-section. Acceptance criteria come from the PRD's functional requirements for this feature, restated in the template's pattern. Exact UI text in quotes. Every formula in words. Name each variant (role, record type, status).
- **Section 5.** One `5.<n>` per screen, panel, modal or grid. Every screen named in Section 4 has a Section 5 entry. A field whose type, limit or default is not in the sources gets an `[ASSUMPTION A-<n>: …]` or a question.
- **Section 6.** Figma links if they exist; otherwise "Not linked".
- **Section 7.** Other PRD features this one depends on or feeds, by `F-<nnn>` (and FRD ID when that FRD exists), with a direction.
- **Section 8.** 8.1: every PRD NFR whose "Applies to" is "All" or names this feature, with its `NFR-<nnn>` id, category and the PRD target word for word, and how it applies here (name the FR ids). 8.2: only needs specific to this feature, as `FNFR-<Fnnn>-<nn>`; one that should apply to other features too becomes a question. 8.3: data volumes; values no source gives are "To be confirmed" with a question.
- **Section 9-11.** From the PRD and the architecture. Unknowns become questions or assumptions.
- **Section 12.** `## 12. Open Questions` with one `- Q-<n>: <question> (raised by <name>)` item per question, numbered from the highest existing id plus one. "raised by" is the user's name when they raised it, otherwise "Fenn". Write "- None." only if there is truly nothing open.
- **Section 13.** Links as given, else "Not linked". Glossary from the PRD's glossary where one exists.

When the sources disagree, do not pick one silently: ask the user, or add a question that names both sources.

### 3. Front matter

Set or keep: `title` (`FRD - <F-nnn> - <Feature Name>`), `frd_id`, `feature` (`F-<nnn>`), `prd_version` (the PRD's front matter `version` now), `ado_feature_id` (or "Not linked"), `date` (today), `version` (keep the existing value; 0 for a new FRD — Warden raises it on approval), `approval_status` (`draft` for a new FRD), and the three confidence fields from step 5.

**Update of an approved FRD:** when the FRD's content changes in this conversation and its `approval_status` is `approved`, set it back to `draft` in the same save, and log `'FRD updated via chat: <one-line summary, no content>'` (`--event FRD_UPDATED`). One log per change, not batched. Re-approval goes through Warden.

**PRD changed since the FRD:** when the PRD's `version` is higher than the FRD's `prd_version`, tell the user before drafting, and check every requirement and inherited NFR against the new PRD.

### 4. Cross-reference check

Before saving the final draft, check and fix what you can:

1. Every `4.<n>` names a Section 5 screen that exists (or says why it has none, for example a background job).
2. Every PRD functional requirement of this feature is covered by at least one `FR-<Fnnn>-<nn>`, and no `FR` id covers scope outside the feature.
3. Every PRD NFR that applies to this feature is in 8.1, with the PRD's target unchanged.
4. Every "To be confirmed" in the document, other than Figma and ADO, has a `Q-<n>` or an `[ASSUMPTION A-<n>: …]` next to it or in Section 12.
5. Question ids run from `Q-1` with no gaps; assumption ids run from `A-1` with no gaps; `FR` ids are unique; no id is used twice.

List any gap you could not fix to the user as a short table (check, where, what is missing). Do not hide a gap by deleting the reference.

### 5. Confidence

Self-assess as the Confidence Scoring facts describe (loaded by the team override). For an FRD, weigh: open questions and assumptions, sections drafted without a source (no UX design, no architecture), cross-reference gaps from step 4, and source conflicts you had to raise. Write `confidence`, `confidence_label` and `confidence_rationale` into the front matter.

### 6. Save and report

Save `{feature-folder}/{agent.frd_filename}` (create the folder if needed). Tell the user:

- the path, the confidence score and its rationale;
- the counts: requirements, screens, inherited NFRs, open questions, open assumptions;
- that no story of this feature can go to development while the FRD has open questions or assumptions or is not approved, and that a named person records each answer as a `Resolved:` line (format in `docs/ready-for-dev-markup.md`);
- the next step: the FRD review (`experion-frd-review`), then approval with Warden. The team override offers both.
